# ESCO skill implementation (Phase 1, 2026-09-27)

Branch `krly/esco-skill-implementation`. Kareerly's curated skills
(`backend/data/skills_reference.csv`, `SK###`) stay the runtime vocabulary;
ESCO v1.2.1 URIs are reference links. The fine-tuned all-MiniLM-L6-v2 model
and every match threshold are unchanged. Inputs: `Kareerly_ESCO_v1.2.1_en_csv.zip`
(SHA-256 `9608b20a…21ad`, not committed) and `Kareerly_ESCO_Skill_Audit.docx`,
whose counts were re-checked against the repository (section 8).

## 1. One shared skill resolver

`backend/app/services/skill_resolver.py` is the only place that decides which
text names which skill, with one normalisation (`normalize`). Everything
that reads skills goes through it:

| Path | Before | Now |
|---|---|---|
| Resume extraction (Step 1/2) | own alias index: every `related_skills` entry and ESCO label, all 694 rows | verified names of active skills |
| Job requirement, typed skill (`_skill_key`) | a second, narrower alias table | the same vocabulary's `resolve` |
| Pasted-job skills | `_skill_key` and the extractor | same |
| Coverage evidence names | a third list (`skill_evidence_phrases`) | the vocabulary's evidence names |
| Learning evidence and gap IDs | the extractor and its own alias table | the shared extractor (all skills' verified names) and `resolve` |
| Fallback extractor that split labels on commas | used when nothing was found | removed |

Statuses in `backend/data/skill_aliases.csv` (generated by
`backend/scripts/build_skill_alias_review.py`; metadata in
`skill_aliases_meta.json`):

| Status | Meaning | Used for |
|---|---|---|
| `verified` | names exactly this skill, both ways | extraction, resolution, coverage, course evidence |
| `one_way` | a phrase that shows the skill, never the reverse | coverage only (`skill_evidence_relations.csv`) |
| `candidate` | unreviewed: ESCO alternative labels, related-concept phrases | nothing, until a person verifies it |
| `excluded` | reviewed and rejected (`skill_alias_exclusions.csv`) | nothing |

Counts: 5,367 names — 955 verified, 57 one-way, 48 excluded, 4,307
candidates (1,131 pass the deterministic filter). Verified sources: 694
Kareerly names, 115 curated tool spellings, 37 reviewed variants, 101 ESCO
preferred labels of reviewed links, 3 bare language names (Python, Java,
JavaScript), 1 reviewed equivalence relation ("data entry" = Data Encoding)
and 4 equivalences already asserted by committed tests (customer care and
customer support = Customer Service, perform CPR = Basic Life Support, land
surveying = Surveying Support; `reviewed_by` says so).

The filter records `skill_not_reviewed`, `ambiguous_in_esco`,
`preferred_label_of_other_concept`, `too_short`, `single_word`,
`category_label`, `names_another_skill` and `protected_look_alike`. It orders
review; a pass does not verify a name ("make business decisions" passes for
Marketing management). Reviewer decisions (`reviewed_by`) survive
regeneration.

Protected pairs, asserted in `tests/test_skill_resolver.py`: Java /
JavaScript, C / C++ / C#, SQL / MySQL, UI / UX Design, Adobe Photoshop /
Adobe Illustrator, SEO / search engine marketing, Microsoft Excel / Microsoft
Office, Data Analysis / Data Science. ESCO traps also tested: "SQL" (also an
ESCO label of database management systems), "bookkeeping" (of accounting),
"MS Excel" (of use spreadsheets software), "SEM".

Case-sensitive spellings ("React", "JS", "Power Point") resolve a
requirement in any case but match running text only as written, so "react to
complaints" is not React.js.

## 2. The 422 unreviewed ESCO auto-expansion skills

They are **inactive for text**: their names are not searched for in resumes
or postings. Their IDs still resolve, so a confirmed skill, a saved match or
a job requirement that stores one keeps its meaning — nobody loses a credited
skill. Course evidence still reads their exact names ("does this course name
Accounting").

`backend/scripts/unreviewed_skill_dependencies.py` inventories them.
Repository result:

| Source | Unreviewed skills referenced | References |
|---|---|---|
| Reference jobs (required and nice-to-have) | 0 | 0 |
| Bundled learning catalogue mappings | 184 | 314 |
| Reviewed name files (variants, relations, exclusions) | 16 | 26 |
| Tests | 14 | 17 |

Proposed actions: 223 inactive_ok (nothing uses them), 190 review_or_retire
(catalogue or test references only), 9 map to their reviewed duplicate.
**Live data was not measured** (Supabase is unreachable from the build
environment). Before retiring any of them, run with `--live` where
`SUPABASE_SERVICE_ROLE_KEY` is set; it counts confirmed skills, skill
progress, saved matches, resume analyses, saved external analyses, live jobs
and live resources (read-only, counts only).

Migration plan: (1) run `--live`; (2) skills with `map_to_SK###`: update
stored IDs to the reviewed one (runtime already treats them as the same);
(3) `review_before_retiring` (candidates hold it): review the skill before
any change; (4) only then mark retired rows, never delete IDs that stored
records use.

## 4. Pasted jobs

Gemma (`gemma_service.py`) is part of the implementation when
`GEMMA_BASE_URL` is set: it parses the posting and may reword the
explanation. It never sets the score, Fit-Now/Aspiration or skill possession.
Without it, `classify_requirements` reads the posting line by line:
requirements headings or "required"/"must have" → required; preferred
headings or "a plus"/"preferred" → preferred; "About us"/"Benefits" →
ignored; anything else → unclassified, scored as nice-to-have (never
required), listed in `metadata.unclassified_skills` and named in a warning.

## 5. Gaps and learning

Gaps stay deterministic: a vacancy's own required and preferred skill IDs
minus the candidate's verified skills. ESCO occupation profiles are not used
as vacancy requirements. A resource is shown for a gap only when a reviewer
verified its mapping or its own title, description or provider skill list
names that skill through verified names; no category or placeholder fill;
completing a course never adds the skill (unchanged, see
`docs/learning-recommendations.md`).

## 6. Evaluation (draft labels)

`backend/evaluation/skill_resolution/` — 97 requirement strings, 56
mock-resume sentences, 50 look-alikes, 60 course links. Labels were drafted
by the assistant (`label_status = draft`) and need a person's review before
the figures are reported as results. None of these items was used to choose
aliases or filter rules; the look-alike subset overlaps the regression tests
and is reported separately. Run:
`backend/.venv/bin/python -m backend.evaluation.run_skill_resolution_eval`.

| Method | Requirements P / R / F1 | Look-alikes P / R / F1 (false matches) | Resume mentions P / R / F1 |
|---|---|---|---|
| A exact labels | 1.000 / 0.861 / 0.925 | 1.000 / 0.611 / 0.759 (0) | 1.000 / 0.846 / 0.917 |
| **B verified (runtime)** | 0.974 / 0.884 / 0.927 | 1.000 / 1.000 / 1.000 (0) | 1.000 / 0.942 / 0.970 |
| B + filter-passing candidates | same as B | same as B | same as B |
| B-raw (all ESCO labels as synonyms) | 0.974 / 0.884 / 0.927 | 0.923 / 1.000 / 0.960 (3) | 1.000 / 0.942 / 0.970 |
| C = B + difflib fuzzy | same as B | same as B | same as B |

Decisions: B at runtime; provisional candidates off
(`PROVISIONAL_CANDIDATE_EXTRACTION = False`); no fuzzy matching (no gain; the
rule was +2 F1 points with no look-alike false match). B-raw's false matches:
SEM and "search engine marketing" as SEO, Scrum as ICT project management
methodologies. B's one requirement false match is "Version Control" → Git
Version Control (a curated alias the draft label disagrees with; for the
reviewer).

Course links (60): the raw catalogue mapping has precision 0.717 (17 of 60
wrong). Requiring the resource's own text to name the skill: precision 0.879,
recall 0.674 on the first run; after letting course evidence read unreviewed
skills' exact names (prompted by that run's misses, so not independent):
precision 0.830, recall 0.907, F1 0.867. Remaining misses are certificates
whose skill list was filled from a category template, which is not evidence.
Caveat: the curated rows' skill lists were written by the catalogue curator
in Kareerly skill names; they are not purely provider text.

Figures after adding Node.js, MySQL, C++ and C# (section 10); four draft
labels that said "not in taxonomy" for those names were changed to the new
skills.

## 7. Match distribution (model and thresholds unchanged)

`diagnose_match_distribution.py`, 33 mock resumes × 460 jobs, before → after:

|---|---|---|
| Fine-tuned cosine, strong p10 / median / p90 | 0.212 / 0.519 / 0.705 | 0.204 / 0.518 / 0.702 |
| Fine-tuned cosine, weak p10 / median / p90 | −0.032 / 0.068 / 0.195 | −0.032 / 0.068 / 0.195 |
| Cosine AUC strong vs weak / strong vs moderate | 0.966 / 0.865 | 0.964 / 0.862 |
| Strong: Fit-Now / Aspiration / Low Match | 134 / 175 / 50 | 133 / 176 / 50 |
| Moderate: Fit-Now / Aspiration / Low Match | 64 / 671 / 1,853 | 63 / 666 / 1,859 |

The small cosine shift comes from the model input, which lists the resume's
extracted skills: unreviewed skills are no longer among them. The one strong

Quality Control only through "Kaizen suggestions" matching an unreviewed ESCO
label; the resume never names quality control. Not material; no threshold
change.

## 10. Additions after the first push

- **Node.js (SK695), MySQL (SK696), C++ (SK697), C# (SK698)** are curated
  skills. Before, "NodeJS" named nothing and SQL/MySQL, C++/C# looked
  distinct only because one side was unknown. MySQL, C++ and C# are linked to
  their ESCO v1.2.1 concepts (preferred label verified, alternative labels
  candidates). "C#" is allowed as a two-character name in text; "C" alone
  names nothing.
- **Step 2 skill search.** `@app.get("/api/skills/search")` decorated the
  `_search_form` helper instead of `search_skills`, so the endpoint never
  answered a query (also on `main`). Fixed; search now reads the shared
  vocabulary's verified names, shows the Kareerly skill name and does not
  offer unreviewed auto-expansion skills or candidate ESCO labels.
- **Supabase reference import.** `scripts/import_reference_data.py` reads the
  ESCO zip directly (skipping `__MACOSX` copies), keeps the latest row of a
  duplicated concept and writes `sql_editor/NN_<table>.sql`: upserts under
  1 MB each, to run in name order in the Supabase SQL Editor after
  `supabase/migrations/20260918090000_occupation_skill_reference.sql`, next to
  the psql `load.sql`. Links of reviewed or mapped skills load as `reviewed`;
  exact-label link proposals use ESCO preferred labels only (Trello, Asana
  and SAP ERP are no longer proposed as broader concepts). Tested on
  PostgreSQL 16: 13,939 skills, 3,039 occupations, 126,051 occupation-skill
  relations and the Kareerly links; a second run changed nothing and kept a
  reviewer's decision. The runtime does not read these tables.
